## 🎯 使用场景

### 场景1: 核心功能变更

**输入**:
```json
{
  "requirement": "支付模块需要支持微信支付和支付宝",
  "git_diff": "+def wechat_pay(): ...\n+def alipay(): ...",
  "context": {"priority": "P0"}
}
```

**流程**:
1. Agent判断: 需要测试（高风险）
2. Strategy生成: API + UI + 集成测试
3. Orchestrator执行: 并行运行
4. Self-Healing: 失败自动修复
5. Report: AI总结风险

**耗时**: ~18s

### 场景2: 文档更新

**输入**:
```json
{
  "requirement": "更新README文档",
  "git_diff": "+## 安装说明\n+...",
  "context": {"priority": "P2"}
}
```

**流程**:
1. Agent判断: 无需测试（低风险）
2. 提前退出: 直接生成报告
3. Report: 说明跳过原因

**耗时**: ~2s

### 场景3: Bug修复

**输入**:
```json
{
  "requirement": "修复订单计算错误",
  "git_diff": "-total = price * count\n+total = price * count * discount",
  "context": {"priority": "P1"}
}
```

**流程**:
1. Agent判断: 需要测试（中风险）
2. Strategy生成: API测试
3. Orchestrator执行: 串行运行
4. Self-Healing: 如有失败则修复
5. Report: AI分析修复效果

**耗时**: ~15s

## 📈 性能优化建议

### 1. Agent阶段优化
- 使用更快的模型（如qwen2.5:1.5b）
- 启用决策缓存（相同需求不重复分析）
- 减少prompt长度

### 2. Orchestrator优化
- 启用并行执行（parallel: true）
- 合理设置并发数（max_workers）
- 优化测试用例执行时间

### 3. 整体优化
- 跳过不必要的阶段
- 使用异步执行
- 启用结果缓存

## 🎓 最佳实践

### 1. 合理设置优先级

- **P0**: 核心功能（支付、登录、订单）
- **P1**: 重要功能（用户管理、商品管理）
- **P2**: 一般功能（日志、配置）

### 2. 提供清晰的需求描述

好的示例:
```
"支付模块需要支持微信支付，包括扫码支付和H5支付"
```

不好的示例:
```
"改了点代码"
```

### 3. 包含有意义的git_diff

好的示例:
```diff
+def wechat_pay(order_id, amount):
+    return process_payment('wechat', order_id, amount)
```

不好的示例:
```diff
+# 添加注释
```

### 4. 使用trace_id追踪

每次执行都会返回唯一的trace_id，保存它以便后续查询：

```python
result = service.run_pipeline(...)
trace_id = result['trace_id']

# 后续查询
trace_result = requests.get(f"/api/pipeline/trace/{trace_id}")
```

## 🆘 常见问题

### Q1: Pipeline执行很慢？
**A**: Agent阶段调用LLM需要时间，可以：
- 使用更快的模型
- 启用缓存机制
- 对于文档变更，会自动跳过

### Q2: 如何查看详细日志？
**A**: 日志保存在 `output/pipeline_logs/` 目录，JSONL格式，可以用文本编辑器打开。

### Q3: 修复失败怎么办？
**A**: Self-Healing最多重试1次，如果仍失败，需要人工介入。查看healing记录了解失败原因。

### Q4: 如何自定义测试策略？
**A**: 修改 `strategy/rules.py` 中的业务规则。

### Q5: 支持哪些测试类型？
**A**: 目前支持 API、UI、Integration 三种类型，可在 `orchestrator/base_runner.py` 中扩展。
