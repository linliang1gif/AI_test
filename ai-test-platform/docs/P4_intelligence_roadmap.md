# 智能化提升路线图

## 当前状态

系统已具备较完整的多类型自动化测试底座，并形成了测试集、测试数据、质量门禁、报告和失败归因闭环。

当前智能化分为三层：

### L1 规则智能 — 已较强（8/10）

不依赖大模型，稳定、可控、可回归：

- 质量门禁 9 条规则
- 敏感数据自动识别
- 变量替换引擎
- 视觉 diff 对比
- 性能阈值判定
- real 模式危险操作拦截
- Web UI 失败规则归因
- selector 稳定性评分
- 数据缺失识别

### L2 LLM 辅助智能 — 有入口但不稳定（5.5/10）

- AI 用例生成 — 功能有，依赖 AI_PROVIDER
- AI 用例评审 — 功能有，依赖 AI_PROVIDER
- AI 报告分析 — 功能有，无 AI 时无降级
- AI 自愈建议 — 基础链路有，受 dry_run/白名单保护，不算成熟
- AI UI 失败解释 — 规则归因可用，AI 增强预留，暂未验证真实 LLM 归因效果

问题：依赖 API Key、成本不可控、质量不稳定、回归常 SKIP、无生成质量闭环、无本地模型兜底

### L3 决策智能 — 基本缺失（3/10）

- ❌ 根据历史失败推荐该测什么
- ❌ 根据代码变更做影响分析
- ❌ 根据模块风险自动选测试集
- ❌ 根据失败趋势预测高风险模块
- ❌ 根据覆盖率缺口推荐补充用例
- ❌ 根据 CI 历史识别 flaky 用例
- ❌ 根据门禁结果给出发布风险建议

> **核心短板不是"没有 AI"，而是缺少基于历史执行数据、代码变更、失败趋势和覆盖率的智能测试决策能力。**
> **后续重点应从"AI 生成内容"转向"AI/规则辅助决策"：测什么、为什么测、风险在哪里、是否允许发布。**

| 测试资产管理 | 8/10 | 用例、测试集、数据集都有 |

## 智能化路线（修正版）

```
P3-3A  测试数据增强与清理机制    ← 智能化地基，数据稳定性
P3-3B  缺陷闭环 MVP            ← 从"发现问题"到"管理问题"
P3-4   质量驾驶舱 MVP          ← 可决策看板，测试负责人最关心
P3-5   智能选测/风险推荐        ← 真正的决策智能
P3-6   AI 生成质量闭环          ← 让 AI 越用越准
P3-7   本地模型适配（可选）     ← 平台稳定后再考虑
```

---

## P3-3A 测试数据增强与清理机制

**目标**：智能化的地基 — 保证执行数据干净、稳定、可复用。

**范围**：
- 数据完整性校验：绑定的数据集是否有缺失 key
- 数据污染检测：执行后数据是否被意外修改
- 执行后清理机制：按 cleanup_rule 类型数据集自动执行清理
- CI 数据隔离：每次 CI 运行使用独立数据快照，互不干扰
- 数据健康报告：数据集使用频率、缺失率、过期项统计

**不依赖 LLM**。

---

## P3-3B 缺陷闭环 MVP

**目标**：从"发现问题"升级到"管理问题"。

**范围**：
- 新增 `defects` 表：记录缺陷，关联 run/case/screenshot/trace
- 失败归因 → 自动创建缺陷建议（规则匹配，非 LLM）
- 缺陷状态流转：open → confirmed → fixed → verified → closed
- 重复缺陷识别：同模块同错误信息自动关联
- 已知问题标记：失败匹配已知缺陷时标记 known_issue，不影响门禁

**核心价值**：让平台从"测试执行工具"变成"质量管理平台"。

---

## P3-4 质量驾驶舱 MVP

**目标**：把已有数据汇总成可决策看板，测试负责人最关心的东西。

**看板内容**：
- 测试集通过率趋势（按天/周）
- 质量门禁结果趋势
- 高风险模块 Top 5（失败率最高）
- 失败类型分布（API/WebUI/Visual/Performance）
- 性能趋势（接口响应时间变化）
- 视觉失败趋势
- Flaky 用例识别（时而过时而不过）
- 数据问题数量
- 用例健康度评分

**新增文件**：
| 文件 | 说明 |
|---|---|
| `services/analytics_service.py` | 历史数据聚合引擎 |
| `routes/analytics_routes.py` | 分析 API 端点 |
| `frontend/src/pages/QualityDashboard.jsx` | 质量驾驶舱页面 |

**不依赖 LLM**，纯数据统计 + 规则评分。

---

## P3-5 智能选测 / 风险测试推荐

**目标**：真正的决策智能 — 告诉用户"这次该测什么、可以跳过什么"。

**输入**：
- 历史失败率
- 用例优先级
- 最近失败时间
- 模块变更（git diff）
- 接口风险评分
- 覆盖率缺口
- 性能退化趋势
- Flaky 情况

**输出**：
- 本次建议执行哪些测试集
- 哪些用例必须跑
- 哪些可以跳过（连续 N 次通过 + 无变更）
- 哪些模块风险最高 → 需要重点覆盖

**风险评分公式**：
```
风险分 = 历史失败率 × 0.4 + 最近变更频率 × 0.3 + (1 - 测试覆盖率) × 0.3
```

**核心用规则引擎，可选 LLM 增强**生成自然语言策略报告。

---

## P3-6 AI 生成质量闭环

**目标**：让 AI 生成的用例越用越准。

**范围**：
- 生成用例自动打标：`ai_generated=true`，追踪执行表现
- 质量指标：通过率、发现真实 Bug 数、冗余率
- Prompt 版本管理：记录版本和生成效果
- 自动优化建议：通过率过低的场景类型提示调整
- 人工修改追踪：AI 生成后被人改了多少 → 评估生成质量

---

## P3-7 本地模型适配（可选，最后做）

**目标**：离线 AI 能力，不依赖外部 API。

**范围**：Ollama / Qwen / DeepSeek 本地蒸馏、embedding 本地化、私有知识库。

**前提**：平台稳定、数据充足、有明确的评估基准后再做。

## 不应该现在做的事

- ❌ 本地大模型（不是接个 Ollama 就完事）
- ❌ AI 自动生成大量测试数据
- ❌ AI 自动修复所有失败
- ❌ AI 自动更新 baseline
- ❌ AI 自动改 selector
- ❌ App/小程序自动化

这些会让系统复杂度暴涨，收益不确定。

## 原则

- ✅ 优先用**统计规则**而非 LLM，保证离线可用
- ✅ LLM 作为**增强层**而非必需层
- ✅ 每个阶段独立可交付，不阻塞
- ✅ 不引入额外基础设施（不加 Redis/Kafka/ML 框架）
- ✅ 复用现有数据库 + 现有执行引擎
- ✅ 方向从"AI 生成内容"转向"AI/规则辅助决策"
