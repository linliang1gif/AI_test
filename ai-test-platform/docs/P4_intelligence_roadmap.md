# 智能化提升路线图

## 当前状态

系统已具备较完整的多类型自动化测试底座，并形成了测试集、测试数据、质量门禁、报告和失败归因闭环。

当前智能化分为三层：

### L1 规则智能 — 已较强（8/10）

不依赖大模型，稳定、可控、可回归：

- 质量门禁 9 条规则
- 敏感数据自动识别
- 变量替换引擎
- 视觉 diff 对比
- 性能阈值判定
- real 模式危险操作拦截
- Web UI 失败规则归因
- selector 稳定性评分
- 数据缺失识别

### L2 LLM 辅助智能 — 有入口但不稳定（5.5/10）

- AI 用例生成 — 功能有，依赖 AI_PROVIDER
- AI 用例评审 — 功能有，依赖 AI_PROVIDER
- AI 报告分析 — 功能有，无 AI 时无降级
- AI 自愈建议 — 基础链路有，受 dry_run/白名单保护，不算成熟
- AI UI 失败解释 — 规则归因可用，AI 增强预留，暂未验证真实 LLM 归因效果

问题：依赖 API Key、成本不可控、质量不稳定、回归常 SKIP、无生成质量闭环、无本地模型兜底

### L3 决策智能 — 已有基础（6/10）

- ✅ 根据历史失败推荐该测什么（P3-5）
- ❌ 根据代码变更做影响分析（需接 Git，暂不做）
- ✅ 根据模块风险自动选测试集（P3-5 suite_recommendations）
- ✅ 根据失败趋势预测高风险模块（P3-4B module-risk + P3-5）
- ❌ 根据覆盖率缺口推荐补充用例（需接覆盖率工具，暂不做）
- ✅ 根据 CI 历史识别 flaky 用例（P3-4B flaky-trend + P3-5 flaky_weight）
- ✅ 根据门禁结果给出发布风险建议（P3-5 gate_failure_weight）

> **核心短板不是"没有 AI"，而是缺少基于历史执行数据、代码变更、失败趋势和覆盖率的智能测试决策能力。**
> **后续重点应从"AI 生成内容"转向"AI/规则辅助决策"：测什么、为什么测、风险在哪里、是否允许发布。**

## P3-3A 测试数据增强与清理机制

**目标**：智能化的地基 — 保证执行数据干净、稳定、可复用。

**范围**：
- 数据完整性校验：绑定的数据集是否有缺失 key
- 数据污染检测：执行后数据是否被意外修改
- 执行后清理机制：按 cleanup_rule 类型数据集自动执行清理
- CI 数据隔离：每次 CI 运行使用独立数据快照，互不干扰
- 数据健康报告：数据集使用频率、缺失率、过期项统计

**不依赖 LLM**。

---

## P3-3B 缺陷闭环 MVP

**目标**：从"发现问题"升级到"管理问题"。

**范围**：
- 新增 `defects` 表：记录缺陷，关联 run/case/screenshot/trace
- 失败归因 → 自动创建缺陷建议（规则匹配，非 LLM）
- 缺陷状态流转：open → confirmed → fixed → verified → closed
- 重复缺陷识别：同模块同错误信息自动关联
- 已知问题标记：失败匹配已知缺陷时标记 known_issue，不影响门禁

**核心价值**：让平台从"测试执行工具"变成"质量管理平台"。

**看板内容**：

- 视觉失败趋势

- 用例健康度评分

## P3-5 智能选测 / 风险测试推荐（已完成）

**目标**：真正的决策智能 — 告诉用户"这次该测什么、可以跳过什么"。

**实际输入数据**：
- 历史失败率（run_cases 通过/失败统计）
- 用例优先级（TestCase.priority / risk_level）
- 最近失败权重（failure_rate × 1.5，衰减）
- 所属模块风险（模块级失败率聚合）
- 未关闭缺陷（Defect 表 open/confirmed 状态）
- Flaky 影响（同一用例在窗口期内同时出现 pass 和 fail）
- 数据问题影响（run summary 中 data_issue 标记）
- 门禁失败影响（run summary 中 gate_status=fail）

**暂未纳入**：
- ~~模块变更（git diff）~~ — 未接 Git 变更分析，不做 Webhook
- ~~覆盖率缺口~~ — 未接代码覆盖率采集工具
- 后续如接入 Git 和覆盖率，可升级为 P3-5B

**输出**：
- 本次建议执行哪些测试集（suite_recommendations）
- 哪些用例必须跑（must_run / should_run）
- 哪些可以跳过（skip_candidate：连续 N 次通过 + 低风险 + 无缺陷）
- 哪些模块风险最高（module_recommendations）
- 每条推荐附带 reasons 理由列表

**实际风险评分公式（8 因子）**：
```
case_risk_score =
  历史失败率        × 0.25
+ 最近失败权重      × 0.20
+ 用例优先级权重    × 0.15
+ 所属模块风险      × 0.15
+ 未关闭缺陷影响    × 0.10
+ flaky 影响        × 0.05
+ 数据问题影响      × 0.05
+ 最近门禁失败影响  × 0.05
```

> 旧版公式 `风险分 = 历史失败率×0.4 + 最近变更频率×0.3 + (1-测试覆盖率)×0.3` 已废弃。
> 因为当前未接 Git 变更分析和代码覆盖率采集，改用基于执行历史的 8 因子模型。

**风险等级**：high (≥0.75) / medium (≥0.45) / low (<0.45)

**推荐等级**：must_run / should_run / optional / skip_candidate

**核心用规则引擎，不依赖 LLM**。可选 LLM 增强生成自然语言策略报告（P3-6+）。

**验证结果**：104/104 PASS，回归 21/21 PASS。

## P3-6 AI 生成质量闭环

**目标**：让 AI 生成的用例越用越准。

**范围**：
- 生成用例自动打标：`ai_generated=true`，追踪执行表现
- 质量指标：通过率、发现真实 Bug 数、冗余率
- Prompt 版本管理：记录版本和生成效果
- 自动优化建议：通过率过低的场景类型提示调整
- 人工修改追踪：AI 生成后被人改了多少 → 评估生成质量

### P3-6 AI Provider 策略（P3-5.1 确定）

| 场景 | 策略 |
|------|------|
| `AI_PROVIDER=none` | P3-6 只验证 `ai_generated` 标记、`prompt_version` 字段、执行效果统计。不调用真实 LLM。核心回归不因此 FAIL。 |
| `AI_PROVIDER` 可用 | 验证 AI 生成、AI 评审、AI 自愈等真实调用链路。 |
| P1-8A / P1-8 长期 SKIP | 标记为外部 AI 依赖，P3-6 不强依赖它们。可新增 AI provider smoke check（可选执行）。 |

**原则**：
1. P3-6 核心功能（标记追踪 + 效果统计）不依赖 LLM
2. LLM 调用链路作为增强层，`AI_PROVIDER=none` 时自动降级
3. 不因 AI Provider 不可用导致核心回归 FAIL

## 不应该现在做的事

- ❌ 本地大模型（不是接个 Ollama 就完事）
- ❌ AI 自动生成大量测试数据
- ❌ AI 自动修复所有失败
- ❌ AI 自动更新 baseline
- ❌ AI 自动改 selector
- ❌ App/小程序自动化

这些会让系统复杂度暴涨，收益不确定。

## 原则

- ✅ 优先用**统计规则**而非 LLM，保证离线可用
- ✅ LLM 作为**增强层**而非必需层
- ✅ 每个阶段独立可交付，不阻塞
- ✅ 不引入额外基础设施（不加 Redis/Kafka/ML 框架）
- ✅ 复用现有数据库 + 现有执行引擎
- ✅ 方向从"AI 生成内容"转向"AI/规则辅助决策"
