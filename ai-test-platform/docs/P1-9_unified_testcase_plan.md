# 测试用例统一入口、接口覆盖率与脚本导出方案

> 版本: v1.0 | 日期: 2026-05-02 | 状态: 方案评审

---

## 一、统一入口原则

### 1.1 定位

| 模块 | 角色 | 面向用户 |
|---|---|---|
| **TestCases 页面** | 统一导入 / 生成入口 | 所有用户 |
| **API 规范模块** | API 资产管理、版本对比 | API 管理员 |
| **SwaggerWorkbench** | 高级导入 / Tag 过滤 / 排错 | 高级用户 |

### 1.2 统一入口支持的导入方式

TestCases 页面提供一个「导入」按钮，弹窗内 Tab 切换：

| Tab | 输入 | 处理链路 |
|---|---|---|
| 需求文档 | .txt / .docx 文件 | AI 解析 → `test_cases` |
| Swagger 文件 | .json / .yaml 文件 | 解析 → `api_specs` → 规则生成 → `test_cases` |
| Swagger URL | URL 地址 | 拉取 → `api_specs` → 规则生成 → `test_cases` |
| YApi Token | 服务地址 + Token | 拉取 → `api_specs` → 规则生成 → `test_cases` |
| 手动创建 | 表单填写 | 直接 → `test_cases` |

### 1.3 不变的底层数据流

```
需求文档 ──→ AI 生成 ──→ test_cases (source=ai_generated)

Swagger/YApi ──→ api_specs (接口资产)
                    │
                    └──→ 规则生成 ──→ test_cases (source=swagger)
```

**关键约束**: 统一入口只是 UI 合并，不改变数据写入链路。Swagger 导入仍然先写 `api_specs`，再关联生成 `test_cases`。

### 1.4 现有模块保留策略

- **API 规范页面**: 保留。用于查看已导入的 API 资产、版本对比、接口详情。
- **SwaggerWorkbench**: 保留。用于 Tag 级精细筛选、大型 Swagger 文档排错、高级过滤。
- **导航菜单**: SwaggerWorkbench 可降级为二级菜单或"高级导入"入口。

## 二、接口用例生成三层模型

### 2.1 模型总览

```
┌─────────────────────────────────────────────────┐
│  L1  规则生成（导入时自动）                        │
│  每个接口 → 1 条正向用例                           │
│  覆盖: 路径、方法、基础连通性                       │
├─────────────────────────────────────────────────┤
│  L2  规则增强 / 参数变异（导入时可自动）             │
│  每个接口 → 3~8 条异常/边界用例                     │
│  覆盖: 参数校验、鉴权、边界值                       │
│  不依赖 AI                                        │
├─────────────────────────────────────────────────┤
│  L3  AI 增强 / 业务风险（用户手动触发）              │
│  高风险接口 → 业务语义场景                          │
│  覆盖: 重复提交、越权、金额篡改等                    │
│  依赖 AI，按需调用                                  │
└─────────────────────────────────────────────────┘
```

### 2.2 L1: 规则生成（当前已实现）

| 项目 | 说明 |
|---|---|
| **触发时机** | 导入 Swagger/YApi 时自动执行 |
| **生成数量** | 每个接口 1 条 |
| **用例内容** | 正向请求 + 基础断言（HTTP 200 + code 字段存在） |
| **数据来源** | Swagger 的 path、method、parameters、requestBody |
| **不负责** | 异常场景、边界值、鉴权 |

当前状态: **已实现**，即 `swagger_to_cases.py` 中的 `_build_case`。

### 2.3 L2: 规则增强 / 参数变异（待实现）

| 项目 | 说明 |
|---|---|
| **触发时机** | 导入时可自动触发（可配置开关） |
| **不依赖 AI** | 纯规则 + 模板，无 token 成本 |
| **生成数量** | 每个接口 3~8 条（取决于参数数量） |

**变异策略表**:

| 变异类型 | 规则 | 示例 |
|---|---|---|
| 必填字段缺失 | 逐个移除 required 字段 | 移除 `name` 字段，期望 400 |
| 空值 | required 字段设为 `""` / `null` | `{"name": ""}` |
| 类型错误 | string 字段传 int，int 字段传 string | `{"age": "abc"}` |
| 超长字符串 | string 字段填充 10000 字符 | `{"name": "a"*10000}` |
| 非法枚举 | enum 字段传不在列表中的值 | `{"status": "INVALID"}` |
| 边界值 | int 字段传 0、-1、MAX_INT | `{"pageNum": -1}` |
| 鉴权缺失 | 不带 Authorization header | 期望 401/403 |
| 不存在 ID | detail/update/delete 传不存在的 ID | 期望 404 或业务错误码 |

**数据来源**: 全部从 Swagger schema 的 `required`、`type`、`enum`、`minimum`、`maximum` 等字段推导，不需要 AI。

### 2.4 L3: AI 增强 / 业务风险场景（后续实现）

| 项目 | 说明 |
|---|---|
| **触发时机** | 用户在用例列表点击「AI 增强」手动触发 |
| **依赖 AI** | 发送接口定义 + 上下文给 LLM |
| **不默认执行** | 避免 token 成本失控 |
| **识别风险接口** | 根据 path/method/字段名自动标记高风险 |

**高风险识别规则**（不需要 AI，规则标记）:

| 风险标记 | 匹配规则 |
|---|---|
| 写入操作 | POST / PUT / PATCH / DELETE |
| 金额相关 | 字段含 amount / price / fee / money |
| 审批流程 | path 含 approve / audit / review |
| 删除操作 | path 含 delete / remove / batch-delete |
| 支付相关 | path 含 pay / charge / refund |

**AI 生成的场景类型**:

- 重复提交（同一请求连续发送 2 次）
- 状态不可逆（已审批的订单再次提交）
- 金额篡改（修改请求中的金额字段）
- 越权访问（用 A 用户 token 操作 B 用户数据）
- 第三方回调失败（模拟回调超时/错误码）
- 数据一致性（并发修改同一资源）

## 三、接口覆盖率模型

### 3.1 第一期: 核心 3 指标

| # | 指标 | 定义 | 数据来源 | 当前水平 | 目标 |
|---|---|---|---|---|---|
| 1 | **API 路径覆盖率** | 有 ≥1 条用例的接口数 / 已导入接口总数 | `api_specs` 表 vs `test_cases` 表 JOIN | ~100%（L1 每个接口都生成了 1 条） | ≥95% |
| 2 | **正向用例覆盖率** | 有正向成功用例的接口数 / 已导入接口总数 | `test_cases` 中 `data_type=valid` 的去重 path | ~100%（L1 都是正向） | ≥95% |
| 3 | **执行覆盖率** | 已执行过的用例数 / 用例总数 | `test_cases` 中 `last_run_status IS NOT NULL` | 极低（大部分未执行） | ≥60% |

**实现方式**: 第一期通过 SQL 聚合查询实现，不需要新增数据模型。

```sql
-- API 路径覆盖率
SELECT
  COUNT(DISTINCT tc.path) as covered,
  COUNT(DISTINCT a.path)  as total
FROM api_specs a
LEFT JOIN test_cases tc ON tc.path = a.path AND tc.status != 'deleted'
WHERE a.project_id = ?
```

### 3.2 后续增强指标（不在第一期）

| # | 指标 | 说明 | 前置条件 |
|---|---|---|---|
| 4 | 参数覆盖率 | 已测参数数 / 接口定义总参数数 | 需要 L2 参数变异用例 |
| 5 | 异常场景覆盖率 | 异常用例数 / 可变异维度数 | 需要 L2 |
| 6 | 断言覆盖率 | 有 ≥1 条断言的用例数 / 用例总数 | 已有数据可统计 |
| 7 | 鉴权覆盖率 | 有鉴权测试用例的接口数 / 需鉴权接口数 | 需要 L2 鉴权变异 |
| 8 | 高风险接口覆盖率 | 高风险接口已覆盖数 / 高风险接口总数 | 需要风险标记 |

### 3.3 展示方式

第一期在 TestCases 页面顶部增加一行覆盖率摘要卡片:

```
┌─────────────────┬─────────────────┬─────────────────┐
│ API 路径覆盖率   │ 正向用例覆盖率   │ 执行覆盖率       │
│   312/320       │   312/320       │   45/1322       │
│   97.5%  ✅     │   97.5%  ✅     │   3.4%  ⚠️      │
└─────────────────┴─────────────────┴─────────────────┘
```

## 四、生成脚本功能定位

### 4.1 当前状态分析

| 问题 | 现状 |
|---|---|
| 数据来源 | 使用旧内存 `test_cases_db`，不是 SQLite v2 数据库 |
| 脚本内容 | `print("执行步骤...")` + `assert True` |
| 真实 HTTP 请求 | 无 |
| 断言逻辑 | 无（assert True 永远通过） |
| 环境配置 | 硬编码 `BASE_URL = "http://localhost:8000"` |
| CI 可运行 | 不可（没有实际请求和断言） |

### 4.2 风险评估

| 风险 | 影响 |
|---|---|
| **虚假通过** | 用户下载脚本运行全绿，误以为测试通过 |
| **误导用户** | 按钮叫"生成脚本"暗示可用于自动化，实际需要全部重写 |
| **维护负担** | 用户基于空壳脚本改了一半发现不对，浪费时间 |

### 4.3 短期建议: 隐藏或实验化

**方案 A (推荐)**: 按钮改名为 **「导出脚本（实验）」**，加 tooltip 说明"当前为脚本模板，需手动补充请求和断言逻辑"。

**方案 B**: 直接隐藏按钮，后续 P1-9E 升级后重新启用。

### 4.4 后续升级标准 (P1-9E)

升级后的 pytest 脚本必须包含:

```python
# 1. 环境变量配置
BASE_URL = os.getenv("API_BASE_URL", "https://dev-recycle.szhibu.com")
TOKEN = os.getenv("API_TOKEN", "")

# 2. 真实 HTTP 请求
response = requests.post(
    f"{BASE_URL}/api/recycle/order/page",
    headers={"Authorization": f"Bearer {TOKEN}", "Content-Type": "application/json"},
    json={"pageNum": 1, "pageSize": 10},
    timeout=10,
)

# 3. 状态码断言
assert response.status_code == 200, f"Expected 200, got {response.status_code}"

# 4. 业务字段断言
data = response.json()
assert data.get("code") == 200, f"业务码异常: {data.get('code')}"
assert "data" in data, "响应缺少 data 字段"

# 5. 数据结构断言（分页接口）
assert "list" in data["data"], "分页响应缺少 list"
assert "total" in data["data"], "分页响应缺少 total"
```

**必须满足**:
- 从 SQLite v2 数据读取用例定义
- 从环境配置读取 base_url 和 token
- 请求参数从用例的 `body` / `query_params` 填充
- 断言从用例的 `assertions` 字段生成
- 可通过 `pytest test_xxx.py` 直接在 CI 运行

## 五、开发路线

### P1-9A: 统一导入入口

| | 内容 |
|---|---|
| **做什么** | TestCases 页面「导入」按钮 → 弹窗 Tab 切换（需求文档 / Swagger 文件 / URL / YApi / 手动创建）。Swagger/YApi 导入走现有后端接口，在弹窗内完成预览和勾选。 |
| **不做什么** | 不重写后端导入逻辑，不删除 SwaggerWorkbench 页面，不改 api_specs 数据模型。 |
| **验收标准** | ① 用户在 TestCases 页面可完成所有类型的用例导入 ② Swagger 导入后 api_specs 表有记录 ③ SwaggerWorkbench 仍可独立使用 ④ 导入后列表自动刷新显示新用例 |

### P1-9B: 用例编辑能力

| | 内容 |
|---|---|
| **做什么** | 用例详情页支持编辑 title、steps、expected、assertions、priority、body。保存调用 PUT `/api/v2/test-cases/:id`。AI 自愈结果可在编辑界面微调后保存。 |
| **不做什么** | 不做 inline 表格编辑（复杂度高），不做批量编辑，不做版本历史。 |
| **验收标准** | ① 点击用例可进入编辑模式 ② 修改后保存成功、列表刷新 ③ AI 自愈 apply 后可在编辑界面二次调整 |

### P1-9C: 接口用例规则增强 (L2)

| | 内容 |
|---|---|
| **做什么** | 导入 Swagger 时，除 L1 正向用例外，自动生成参数变异用例: 必填缺失、空值、类型错误、超长、边界值、鉴权缺失、不存在 ID。每条用例标记 `data_type` 和 `expected_behavior`。 |
| **不做什么** | 不做 AI 增强（L3），不做业务语义场景，不做并发测试。 |
| **验收标准** | ① 每个 POST/PUT 接口至少生成 3 条异常用例 ② 异常用例的 expected_behavior 为 client_error ③ 必填字段缺失用例覆盖所有 required 字段 ④ 总用例数量从约 1300 增长到 4000+ |

### P1-9D: 接口覆盖率统计

| | 内容 |
|---|---|
| **做什么** | 新增 GET `/api/v2/test-cases/coverage` 接口，返回 3 个核心指标。TestCases 页面顶部展示覆盖率卡片。按项目维度统计。 |
| **不做什么** | 不做参数级覆盖率，不做增强指标，不新增数据表。 |
| **验收标准** | ① API 返回 api_path_coverage / positive_coverage / execution_coverage 三个百分比 ② 页面顶部显示覆盖率卡片 ③ 切换项目时覆盖率跟随刷新 |

### P1-9E: 生成脚本隐藏 / 实验化 / 后续升级

| | 内容 |
|---|---|
| **做什么** | 短期: 按钮改名「导出脚本（实验）」+ tooltip 提示。后续: 从 SQLite 读取用例数据、生成包含真实 requests 请求和断言的 pytest 脚本、支持环境变量和 CI 运行。 |
| **不做什么** | 短期不升级脚本内容，不删除功能。 |
| **验收标准** | 短期: ① 按钮显示「实验」标记 ② tooltip 说明局限性。后续: ① 下载的脚本可直接 `pytest` 运行 ② 断言覆盖状态码 + 业务码 + 数据结构 ③ 支持环境变量配置 base_url 和 token |

## 六、最终建议

| # | 问题 | 结论 | 理由 |
|---|---|---|---|
| 1 | 是否马上做统一入口？ | **是** | 工作量小（扩展现有弹窗），用户体验提升大，消除页面跳转困惑 |
| 2 | 是否马上升级脚本生成？ | **否** | ROI 低，平台内已有执行引擎，脚本导出不是核心链路 |
| 3 | 是否应该先隐藏或实验化生成脚本？ | **是，改名实验** | 当前 assert True 有虚假通过风险，改名可降低误导 |
| 4 | 当前接口覆盖率是否够用？ | **不够** | 只有正向连通性，无异常/边界/鉴权覆盖，但先做统计再做增强 |
| 5 | 下一步最应该先做什么？ | **P1-9A → P1-9B** | 统一入口解决用户困惑，编辑能力是自愈/评审的前置依赖 |
